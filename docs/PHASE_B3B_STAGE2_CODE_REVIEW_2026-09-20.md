## 索引块提案 v2 复审（仍未批准）

v2 将客户端块内容与服务端冻结的逐块摘要计划核对，解决了 v1「每页重读整个 manifest」的主要矛盾，但仍有以下必须先封闭的协议缺口：

1. 批次文档内 `prepPlan` 估算最多约 40KiB；`indexDeclarePage` 每页读取该计划加最多 32KiB 块，不能声称整页仅处理 ≤32KiB。可把批次冻结为常数大小的计划根，用每块的有序 Merkle 证明或等效小型承诺核验内容；若另设计划分片，也要计算其创建/读取/清理预算。原提案的「313 块上限」只是 10000÷32 的满载下界；按字节切页可产生更多块，计划和事务上界须重新推导。
2. 单个 `file` 条目因 `referencedBy` 超过 32KiB 就 `package-rejected`，会拒绝阶段一可合法产出的、多个报告共用同一附件的完整包。须按报告引用分页形成独立承诺条目/侧车块，保持原文件与每个 `{reportId,order}` 的双向闭包，`attachFile` 能按冻结引用分页恢复，而非降低格式接受范围。
3. `finalizeDeclare` 写明 `blockIndex===prepCursor`，却声称同块重放可成功；游标已前进或最后一块已把状态改为 `indexing` 时，丢响应后重试会被拒。明确 `blockIndex<prepCursor` 与末块终态的纯比对幂等返回、相同内容零推进、不同内容冲突；超前块拒绝。预处理的最后一片上传、计划冻结、`abandon` 抢占需要逐个定义事务读写顺序，以免 chunk 或块在清理后落盘。
4. 末片的「一次读 128 分片≈1s」只是未经云端测量的估计。区分一次性 4MiB 验证/派生预算和每次 ≤32KiB 索引页预算，计算最坏文档字节、事务操作、函数超时与故障续跑；单条/多引用/万条记录与末块重放须进入独立验收矩阵。

## 索引块提案 v3 首轮复审（未批准）

常数 Merkle 根与引用侧车的方向可行，但 v3 的数学边界和证明位置尚不能支撑「每页有界、全部块已核验」的验收：

1. `entries<=11276` 只能推出 `blocks<=11276`，**不能**推出 `blocks<=ceil(11276/32)=353`；后者是恰好装满 32 条时的下界。按实际字节切块时可能每块只有一条大的 refs part。应按最大单条/最小装载和 4MiB manifest 字节推导真正上界，或以条目总数作为保守上界；证明深度与 abandon 分页次数随之更新。`refs parts<=ceil(4MiB/16KiB)+500` 也必须说明每个非末 part 的最小装载保证及 JSON 封套/重复字段开销，不能把「上限 16KiB」误当「每片至少 16KiB」。
2. Merkle 叶摘要只包含块内容；`finalizeDeclare` 若只按客户端给的 sibling 方向折叠校验根，没有从服务端冻结的 `blockIndex/totalBlocks` **推导并验证路径位置和树形高度**，合法块 A 可连同 A 的证明在 B 的序号提交，从而重复 A、漏掉 B，最后一块仍把状态置 `indexing`。叶或验证器必须绑定位置与总块数，末块再核对累计条目数、预期根和顺序；重复/缺块、换序以及末块重放应有独立探针。
3. 一页「块 ≤32KiB」未计块文档封套、批次字段、索引写入及 Merkle 证明的处理字节。给出各类最大序列化字节与每调用端到端预算，必要时把块净荷缩到 32KiB 以下。末片一次性读取与解析也需有可验证的超时/重试方案；「约 1s」仅是待测猜想。当前 `mc-restore` 未检查重组后的 manifest 长度 ≤阶段一 4MiB 上限，而允许 128×40KiB 分片，这与此处按 4MiB 推导 refs 上限互相矛盾，应先补限制并测试超界零推进。
4. `attachFile` 从 refs 侧车分页读取的进度和回执丢失重放尚无协议。单个文件可被大量报告引用；必须定义每次调用处理多少 refs、如何原子登记 `mc_files` 与恢复声明、如何保存游标并防止重复追加或清理漏引用。`abandon` 须清除这些 sidecar 声明与已登记引用，不能只说沿用旧清理组。零声明包也须区分无 records/files/refs 与可带 domain-json 文件的空域清单。
5. v3 估算单条记录约 380B 借用了恢复端 `decl.id.length≤128`，但阶段一 `validateManifest` 对 `decl.id` 只要求字符串，导出器对存储 ID 原样投影，尚未证明所有阶段一合法包都有 128 字符上限。任何用此假设推出「合法包绝不超单条大小」或 refs 装载率，必须先给出阶段一/真实数据的约束依据；否则按实际 4MiB 清单容纳的最坏长 ID 处理，避免误拒备份。

批准条件仍是确定性块生成、按位置的证明、单页事务/字节上界与崩溃重放协议完全一致后再编码；目前不得依据 v3 实现索引。

## 索引块提案 v4 复审（未批准）

v4 的位置绑定叶摘要修正了 v3 的换位证明问题，manifest 4MiB 限制亦已见于在途源码；但以下边界仍不能据此实现：

1. `decl.id≤128` 在阶段一并无格式保证，因此「记录条目≤512B」「单 ref≤128B」「合法包不会触发单条 fail-stop」未成立。极长但仍在 4MiB manifest 与相应 domain-json 限额内的 ID 可以是合法备份。必须给出真实 v1 规范的上界证明，或设计不误拒长条目的分片表示；不允许把新的 512B/128B 限制当作保守处理。
2. `≤32 条` 同样会先于 28KiB 触发切页：32 条短条目的块可能只有几 KiB，故「每个非末块>12KiB」并不成立。即便假设总条目字节≤8MiB，按 12KiB 也只能算出约 683 块，推不出 `totalBlocks≤520`；以 520 为硬拒绝上限会误拒合法 full 包。refs parts 的 757 上限也建立在未证明的单 ref 128B 与 `referencedBy` 总字节≤4MiB 的映射转换之上。需给出对任意合法 v1 包都成立的字节和条目数双约束推导及反例探针；不能用 fail-stop 替代格式兼容性证明。
3. 主设计 §5.1 的 `indexDeclarePage` 明写「≤200 条/页（≤32KiB 处理，响应 ≤256KiB）」；前段总表中的「或」表述应随之澄清，不能用条数绕过处理字节约束。v4 的表格自身宣称每页≤48KiB，而且列项 28+1+0.5+0.7+18=48.2KiB，算术亦不成立；32 条声明落库字节≤18KiB 没有逐类序列化证明，输入与输出副本也必须说清如何计入「处理字节」。需选择符合主合同的实际页预算，或先正式修订主设计及客户端/测试约束，不可直接实现超标页。

**v9 复审继续待定。** 编码方的真实整包 H 样本已把 2000×1900B 的反例纳入探针，记录 4000 片、667 块，且另用 I 样本覆盖 refs 非满载分组。但新的 `Nfrag≤ceil(M/1400)+floor(M/2KiB)` 仍把每个触发分片的 manifest 条目只计一个末片：同一个 file 条目可同时把 `path` 和 `originalFileId` 分片，且超大的 `chunkSha256` 数组会先触发短字符串分片；需逐类按实际最多可分片字段数及数组触发条件收费。文中 `floor(4MiB/2KiB)=2149` 也非该式数值（实际 2048），不能靠算错方向的松弛冒充推导。`S` 在 12MiB 硬顶时又沿用旧的 `N≈18000` 算 `1536+374=1910`，按本稿 `N=29332` 应是约 `1536+612=2148`，超过硬性 2048 块；虽声称合法包实际 `S≤10.03MiB`，此结论须建立在已修正且可复查的收费证明上。

**v10 新的实际兼容性阻塞。** 为证明每条 *frag 流源字段 >1KiB，探针把 file 的 `path`/`originalFileId` 只在单字段字节数 >1024 时分片；但一个合法附件可同时有约 1000B 的 path 和约 1000B 的 originalFileId。连同摘要、chunkSha256、contentType、fileIndex 和键名，派生 file core 超过 2KiB；两个字段都不满足新阈值，单块摘要数组拆出后 core 仍过 2KiB，`deriveEntries()` 直接抛错。阶段一并未限制这两个字段到更短值。必须用真实报告映射+附件段+domain-json 字节构造 `validatePackage ok` 的样本覆盖，并修订分片策略，不能为了收费公式让合法 full 包无法恢复。v10 所称 `24³` 分配网格只是有限取样，未证明网格点之间及分支阈值处的全域最坏界；须把它标为压力搜索而非形式证明，或用单调/线性分段上界证明网格足以覆盖。

**abandon 的可完成性还需单独设计。** v10 把 10000 条记录各 103 个极小分片计为最多 1,030,000 条 record_chunks，按 50 文档/调用需 20,600 次调用，又称“后台渐进清理”；但当前未定义云端定时工人、客户端自动续扫或批次总分片/字节预算。两条 `abandoning` 批次会一直占满成员的两个活跃槽位，若用户关掉小程序后无人续调用，后续 begin 也被挡住。必须在满足合法 full 包兼容的前提下限制未完成分片数量/总字节、给出真实可达的清理页数与重启续办触发，或指定可信后台清理执行者。不可仅说游标可恢复就称用户可完成。

v12 初稿用 `Σ记录字节≤24MiB` 推出 `record_chunks≤⌈24MiB/40KiB⌉+10000`，但现有 `uploadRecordChunk` 接受任意非空且≤40KiB 的片；10000 条各用 103 个 1B 片即可产生 103 万文档，同时总上传字节只有约 1MiB，故此推论暂不成立。须在写入前强制服务端规范分片大小（例如除最后一片外恰 40KiB）并在首片锚定前固定总片数、总字节预算，考虑未完成记录和并发 CAS，且以完整阶段一包经客户端重新分片验证兼容。`begin` 一次内联清运 32 页也要核算真实 CloudBase 调用时限，页面重启/重试需有明确驱动者。

v11 所写 `sN*=8.20e-4/B` 与探针的 `1/minDecl≈1/122≈8.20e-3/B` 相差十倍；`sS*=1.644/B` 乘 4MiB 再加常数已约 6.8MiB，不能同时声称 `S≤6.5MiB`。闭式证明必须按实际派生条目逐类列出每个最小尺寸、斜率、固定项及取整，不可用探针中的近似信封当作普适上界。当前仅 J 场景的真实整包修复有独立证据，索引代码仍待设计批准。

聚合上限生产补丁首轮复审：`aggregateRecordBytes` 虽在新片事务中累加，`MAX_BATCH_RECORD_BYTES` 检查却只在已有 anchor 分支；新记录首片走 `else` 即绕过检查，现有自测只覆盖旧 anchor 的边界。达到 24MiB 后另起一条记录仍可写入，推翻声称的全批次 10,615 片界。已要求编码方把上限检查移到两分支共同路径，独立 TESTING 覆盖首片越界与事务零写。该补丁未验收。

独立 TESTING 的 A9 探针对 1640 块包络的数值、已选逐类样本及对抗整包复算为 13/13；它验证了算术和所试样本（历史最坏 716 块），不能单凭有限样本替代全部阶段一有效形状的数学证明。尚需把各类重复字段开销和可选字段与实际序列化的一致性审完再批准索引。L22a 实测无域过滤时 450 个物理分片可逐页前进——此前“400 个物理分片令游标停滞”的评审误判已撤回。L22b/c 找到另一真实边界：给 `domain=mood` 传来自 bag 域的游标，超过四轮的他域行被跳过，返回空 items、原游标和假 `hasMore=false`。设计裁定域过滤游标必须匹配当前批次/域，否则 `invalid-params`，不得把跨域游标解释成“无数据”。规范 40KiB 非末片检查在较早冻结快照的独立 L23 中为绿；聚合上限及跨域游标修正须在新的同源快照重验。

TESTING 的 P10/P11 探索构造了 `validatePackage` 接受的完整容器包：附件可缺 `originalFileId`；零长附件可缺 `chunkSha256`。当前索引探针无条件把两属性放进 file core，规范序列化遇 `undefined` 抛错。实际导出器通常显式产生两字段，故须区分“真实导出器输出合同”和“容器验包允许的更宽集合”；若设计继续声称对一切源验收的 full 包兼容，就必须让索引派生与缺席字段、后续文件身份语义相容，并补端到端原件路径验证。索引实现继续暂停，等待 V14 及完整独立证据。

V14 探针按属性在场与否派生 core，P10/P11 本地整包自检通过；仍有两条未封闭：其一，`originalFileId` 缺席时提议以附件 SHA 作身份，两个不同 fileIndex、相同内容的附件会碰撞，隔离身份应至少包含 batchId+fileIndex，内容摘要只用于验字节；其二，P10 的报告正文附件恰 `{order}`，现有 `validateRecordShape` 要求 `{fileId,order}` 且与冻结映射全等，故索引阶段放行后 `uploadRecord/finalizeRecord` 仍会拒绝。设计应明确全部 `validatePackage` 有效 full 包与真实导出器子集的支持范围；若收窄，服务端须在 declare 阶段明确拒绝且不动原包，不能让一份已索引的包半路才失败。V14 的标题与 6.79MiB 数字还留旧稿口径，批准前同步。

V14 扩大可选字段集合后，形式证明的 `minFileEntry=172B`（含 `originalFileId:''` 与 `chunkSha256:[]`）不再是该类的最小序列化尺寸；须按零长、双字段缺席等所有合法附件形状重算文件类斜率并复核总界。`String(body.fileId)===String(mapping.originalFileId)` 是阶段一逐项验包规则，即使两键都缺席也必须保持同型比较；简单地“只有 fileId 存在才比较”会放过错位引用。V14 后续批次实现 P10 时需验证整段 declare→index→upload→attach→commit→preview，而非只验索引派生。

V15 虽开始自足写状态机，但 §4.3 的声明写入清单缺 `filefrag` 键，拆出的 `path/originalFileId` 分片落不到任何集合；同节要求 record 声明含从冻结 manifest 取得的 `frozenReportAttachments`，大报告映射可超过 32KiB 页面处理预算，而且每页取原 4MiB manifest 将重现索引块原始阻塞。需定义小页侧车映射及 `uploadRecord` 的分页交叉验证，不能把映射塞进一个 record 声明。§7 仍写“与 v14 完全一致”，旧稿已覆盖，须把清理页表和驱动者真正写入自足协议；`finalizeDeclare` 在 abandoning 期的已提交块重放不得误报成功，块文档也须明确只存 blockByteLength 而不重复 10KiB 载荷。索引生产实现仍未获批。

## `progress/list` 在途静态复核（未验收）

编码方已增加两个只读 handler，均经 `resolveCaller`，`progress` 先取 owner batch，`list` 用 ownerMemberId+familyId 条件查询。当前 `progress` 按条数限页，却把声明的完整 `id`/`originalFileId` 直接加入响应；v7 自己已证实合法 full 包的 ID 可达数百 KiB，主设计响应上限为 256KiB，单条就会越界。修复应与长 ID 的请求/预览方案同一协议，使用短承诺/分片游标，响应需按实际序列化字节计量。

未来声明集合含 `idfrag/filefrag/ridfrag/cshafrag/refs` 等物理条目；`progress` 当前对所有非 `record` 项都当 `file`，必须在索引实现时明确只遍历逻辑声明或过滤物理类型，否则会把碎片错误展示为附件、造成游标/完成率不一致。`hasMore` 只按当前页是否满判断，末页恰好页长会多给一个空页；若契约要求精确布尔值，应预读一个边界项或承认这种续页语义。`list` 新查询需要部署索引与实际分页稳定性测试，不能仅凭静态阅读验收。上述由独立 TESTING 以冻结源码复现后再裁定。

**V15 修正版仍退回（约 06:42）。** `refs` 条目按 fileIndex 编排，仅承载 `{order,rid}`；新提议的 `<batchId>:declmap:<fileIndex>:<part>` 并不能以报告的声明索引有界地取回该报告按 `order` 排列的所有附件映射，也未包含从 `order` 到 `fileIndex` 的完整可检索关系。`record` 条目没有 `refsCount`，索引页不能在不重新读取整份 manifest 的条件下凭空写出该字段；“每报告侧车 part 数 = refsCount”则把分片数与附件数混为一谈。此外，`refs part` 已写一次声明，再写一份 `declmap` 会增加本页写操作与清理文档数，现有 50 ops / 1,305 页上界随即失效。已要求编码代理在冻结计划中显式派生按报告索引和附件序号键控的映射流与侧车，给出巨型报告 ID、分片文件身份的有界检索及逐字节/逐操作新证明，审核前索引生产仍暂停。
